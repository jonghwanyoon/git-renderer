# CORS 문제 해결 가이드

## CORS란?

브라우저에는 **"같은 출처 정책(Same-Origin Policy)"**이라는 보안 규칙이 있습니다.

쉽게 비유하면:

```
당신이 A아파트(github.io)에 살고 있는데,
B아파트(회사 GitLab)의 택배함에서 물건을 가져오려 합니다.

→ 경비원(브라우저)이 "다른 아파트 주민은 안 됩니다" 하고 막습니다.
→ 이것이 CORS 차단입니다.
```

**CORS**(Cross-Origin Resource Sharing)는 브라우저가 **다른 도메인**의 데이터를 가져오는 것을 제한하는 보안 정책입니다. 서버가 명시적으로 허용하지 않으면 브라우저가 요청을 차단합니다.

## 왜 문제가 되나요?

git-renderer를 GitHub Pages에 배포하면 이런 상황이 됩니다:

```
┌─────────────────┐          요청           ┌──────────────────────┐
│  GitHub Pages   │  ───────────────────►   │  회사 인트라넷 GitLab  │
│  (A 도메인)      │                         │  (B 도메인)            │
│                 │  ◄── 브라우저가 차단! ──  │                      │
└─────────────────┘                         └──────────────────────┘

  git-renderer가                              GitLab API에
  여기서 실행됨                                데이터를 요청
```

브라우저는 A 도메인(github.io)에서 B 도메인(회사 GitLab)으로 보내는 요청을 차단합니다. 이것은 **토큰이 있어도** 마찬가지입니다 — CORS는 토큰과 무관한 브라우저 보안 정책입니다.

## 에러 화면 식별법

CORS 문제가 발생하면 git-renderer에 다음과 같은 메시지가 표시됩니다:

> **gitlab.company.com에 연결할 수 없습니다. 다른 도메인(username.github.io)에서 요청하면 브라우저 보안(CORS)에 의해 차단됩니다. 해결: git-renderer.html 파일을 다운로드하여 로컬에서 열어보세요.**

브라우저 개발자 도구(F12)의 콘솔에서는 다음과 같은 메시지를 볼 수 있습니다:

```
Access to fetch at 'https://gitlab.company.com/...' from origin
'https://username.github.io' has been blocked by CORS policy
```

## 해결 방법

### 방법 1: 로컬에서 열기 (가장 간단)

`git-renderer.html` 파일을 다운로드하여 내 컴퓨터에서 직접 열면 CORS 문제가 없습니다.

```
1. git-renderer.html 파일 다운로드
2. 파일을 더블클릭하여 브라우저에서 열기
3. 회사 GitLab URL 입력 → 정상 작동!
```

**왜 되나요?** 로컬 파일(`file:///...`)에서 요청하면 "출처"가 없으므로 CORS 정책이 적용되지 않습니다.

**장점**: 설정 없이 즉시 사용 가능
**단점**: 각자 파일을 다운로드해야 함, 링크 공유 불가

### 방법 2: 인트라넷 웹서버에 배포

회사 인트라넷의 웹서버에 `git-renderer.html`을 올리면 같은 네트워크에서 접근하므로 CORS 문제를 피할 수 있습니다.

```
┌──────────────────────┐         요청          ┌──────────────────────┐
│  인트라넷 웹서버      │  ──────────────────►  │  인트라넷 GitLab      │
│  (intra.company.com) │                       │  (gitlab.company.com) │
│                      │  ◄── 허용 가능! ────  │                      │
└──────────────────────┘                       └──────────────────────┘
```

**방법**:
1. IT팀에 요청하여 인트라넷 웹서버에 `git-renderer.html` 파일 배포
2. 또는 팀 내 간단한 웹서버(nginx, Apache 등)에 파일 배치

**장점**: 팀원 모두 링크로 접근 가능
**단점**: IT팀 협조 필요, 서버 관리 필요

> **참고**: 같은 인트라넷이라도 도메인이 다르면 CORS가 발생할 수 있습니다. GitLab 서버와 같은 도메인에 배포하는 것이 가장 확실합니다.

### 방법 3: GitLab 관리자에게 CORS 허용 요청

GitLab 서버 설정에서 특정 도메인의 요청을 허용하도록 CORS 헤더를 추가할 수 있습니다.

**GitLab 관리자에게 요청할 내용**:

> GitLab API 응답에 다음 CORS 헤더를 추가해주세요:
> ```
> Access-Control-Allow-Origin: https://your-github-pages-domain.github.io
> Access-Control-Allow-Headers: Private-Token
> ```

**장점**: 근본적 해결, GitHub Pages에서 바로 사용 가능
**단점**: GitLab 관리자 권한 필요, 보안 검토 필요

## FAQ

### Q: 토큰을 입력하면 CORS가 해결되나요?

**아니요.** CORS는 토큰과 무관합니다. CORS는 브라우저가 "다른 도메인에 요청 자체를 보내지 않는" 정책이므로, 토큰이 있어도 요청이 차단됩니다.

### Q: VPN을 연결하면 되나요?

**아니요.** VPN은 네트워크 접근 문제를 해결하지만, CORS는 네트워크가 아닌 브라우저의 보안 정책입니다. VPN으로 GitLab에 접속할 수 있더라도 CORS 차단은 그대로입니다.

### Q: 브라우저 확장 프로그램으로 우회할 수 있나요?

CORS를 비활성화하는 브라우저 확장 프로그램이 있지만, **보안상 권장하지 않습니다.** 모든 사이트에서 CORS가 해제되어 보안에 취약해질 수 있습니다. 위의 방법 1(로컬 파일)이 더 안전합니다.

### Q: 같은 네트워크인데 왜 차단되나요?

CORS는 네트워크 위치와 무관합니다. 브라우저가 판단하는 기준은 오직 **도메인(URL)**입니다. `github.io`와 `gitlab.company.com`은 도메인이 다르므로 같은 네트워크 안에 있어도 차단됩니다.
